# All-Zero `TLSInnerPlaintext` Is Mapped to `INVALID_RECORD` Without `unexpected_message`

## Summary

This is a confirmed issue. [RFC 8446 Section 5.4](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.4) requires a receiver that finds no non-zero octet in the AEAD-decrypted cleartext to terminate the connection with an `unexpected_message` alert. The mbedTLS TLS 1.3 receive path instead returns `MBEDTLS_ERR_SSL_INVALID_RECORD` without scheduling or sending that alert. A focused runtime probe reproduced the behavior.

## Standard Requirement

- Standard: [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html)
- Section: [5.4, Record Padding](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.4)

```text
Implementations MUST limit their scanning to the cleartext returned
from the AEAD decryption.  If a receiving implementation does not
find a non-zero octet in the cleartext, it MUST terminate the
connection with an "unexpected_message" alert.
```

This rule specifies an exact condition and an exact alert: after successful AEAD decryption, scan only the returned cleartext, and terminate with `unexpected_message` if it contains no non-zero octet. [RFC 8446 Section 6](https://www.rfc-editor.org/rfc/rfc8446.html#section-6) further defines `unexpected_message` as the alert for an inappropriate message rather than a generic local error.

## Relevant Source Code

### `library/ssl_msg.c:496`

```c
static int ssl_parse_inner_plaintext(unsigned char const *content,
                                     size_t *content_size,
                                     uint8_t *rec_type)
{
    size_t remaining = *content_size;

    do {
        if (remaining == 0) {
            return -1;
        }
        remaining--;
    } while (content[remaining] == 0);
```

After TLS 1.3 decryption, the function scans `TLSInnerPlaintext` backward for the first non-zero octet. It fails when every byte is `0x00`.

The generic stream-TLS invalid-record branch automatically sends only `bad_record_mac` for `MBEDTLS_ERR_SSL_INVALID_MAC`. It does not send `unexpected_message` for this `MBEDTLS_ERR_SSL_INVALID_RECORD` result.

## Implementation Behavior

The inbound record is successfully AEAD-decrypted, and `ssl_parse_inner_plaintext()` scans the resulting cleartext backward. With an all-zero plaintext, the scan fails. The caller maps the failure to `MBEDTLS_ERR_SSL_INVALID_RECORD`, and the outer record path returns that error without scheduling `unexpected_message`. The record is rejected, but its peer-visible failure behavior does not match RFC 8446 Section 5.4.

## Inconsistency Reason

RFC 8446 requires both connection termination and an `unexpected_message` alert for an all-zero decrypted cleartext. mbedTLS terminates processing but collapses the condition into a local `MBEDTLS_ERR_SSL_INVALID_RECORD` error and leaves no pending alert. The observable protocol behavior is therefore non-compliant.

## Runtime Evidence

A focused probe passed an all-zero decrypted `TLSInnerPlaintext` through the TLS 1.3 record-reading path, then ran a valid application-data record through the same path as a control. The test was run twice, with identical results.

The rerun produced:

```json
{"case":"all_zero_inner_plaintext","ret":-29184,"send_alert":0,"alert_type":0,"alert_reason":0,"in_msgtype":0,"in_msglen":0}
{"case":"valid_application_data_control","ret":0,"send_alert":0,"alert_type":0,"alert_reason":0,"in_msgtype":23,"in_msglen":1}
```

`-29184` is `MBEDTLS_ERR_SSL_INVALID_RECORD`. For the all-zero case, `send_alert`, `alert_type`, and `alert_reason` all remained zero, demonstrating that no fatal alert was scheduled. The valid control returned `0` and delivered record type `23` with one byte, showing that the probe and shared record path worked and that the failure came from the targeted condition.

## Impact

- The peer cannot observe the RFC-required `unexpected_message` alert.
- Negative TLS 1.3 conformance tests observe the wrong failure semantics.
- Collapsing the condition into generic `INVALID_RECORD` reduces diagnostic precision.

## Fix Direction

- Add a dedicated branch for the no-non-zero-octet failure from `ssl_parse_inner_plaintext()` in the TLS 1.3 receive path.
- Schedule and send `MBEDTLS_SSL_ALERT_MSG_UNEXPECTED_MESSAGE` before returning the local error.
- Limit the change to the exact RFC 8446 Section 5.4 condition so unrelated record-parse failures are unaffected.
