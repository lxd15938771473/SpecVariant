# TLS 1.3 Protected Handshake Records Ignore the Negotiated `record_size_limit`

## Summary

- Scope: TLS 1.3 builds with `MBEDTLS_SSL_RECORD_SIZE_LIMIT` enabled when the peer negotiates a smaller limit

This is a runtime-confirmed issue in the protected-handshake send path. mbedTLS parses and stores the peer's `record_size_limit`, and its application-data path uses the value, but protected handshake messages such as Certificate bypass the same bound. After the client advertised `RecordSizeLimit = 513`, the server sent one protected handshake record with `848` bytes of plaintext and `864` bytes after encryption, which the client rejected.

## Standard Requirement

- [RFC 8446 Section 5.4, Record Padding](https://www.rfc-editor.org/rfc/rfc8446.html#section-5.4)
- [RFC 8449 Section 4, The `record_size_limit` Extension](https://www.rfc-editor.org/rfc/rfc8449.html#section-4)

```text
The presence of padding does not change the overall record size
limitations: the full encoded TLSInnerPlaintext MUST NOT exceed 2^14
+ 1 octets. If the maximum fragment length is reduced -- as, for
example, by the record_size_limit extension from [RFC8449] -- then
the reduced limit applies to the full plaintext, including the
content type and padding.
```

RFC 8449 defines the received value as the maximum plaintext record size the peer is willing to receive and applies it to records carrying both application data and protected handshake messages:

```text
When the "record_size_limit" extension is negotiated, an endpoint
MUST NOT generate a protected record with plaintext that is larger
than the RecordSizeLimit value it receives from its peer.
Unprotected messages are not subject to this limit.
```

The bound applies to the full `TLSInnerPlaintext`, including content type and padding. TLS 1.3 EncryptedExtensions, Certificate, CertificateVerify, Finished, and other protected handshake records must obey the peer's value.

int mbedtls_ssl_tls13_parse_record_size_limit_ext(mbedtls_ssl_context *ssl,
                                                  const unsigned char *buf,
                                                  const unsigned char *end)
{
    const unsigned char *p = buf;
    uint16_t record_size_limit;

    MBEDTLS_SSL_CHK_BUF_READ_PTR(p, end, 2);
    record_size_limit = MBEDTLS_GET_UINT16_BE(p, 0);

    if (record_size_limit < MBEDTLS_SSL_RECORD_SIZE_LIMIT_MIN) {
        MBEDTLS_SSL_PEND_FATAL_ALERT(
            MBEDTLS_SSL_ALERT_MSG_ILLEGAL_PARAMETER,
            MBEDTLS_ERR_SSL_ILLEGAL_PARAMETER);
        return MBEDTLS_ERR_SSL_ILLEGAL_PARAMETER;
    }

    ssl->session_negotiate->record_size_limit = record_size_limit;
```

### `library/ssl_tls.c:2820`

size_t mbedtls_ssl_get_output_record_size_limit(const mbedtls_ssl_context *ssl)
{
    const size_t max_len = MBEDTLS_SSL_OUT_CONTENT_LEN;
    size_t record_size_limit = max_len;

    if (ssl->session_negotiate != NULL &&
        ssl->session_negotiate->record_size_limit >= MBEDTLS_SSL_RECORD_SIZE_LIMIT_MIN &&
        ssl->session_negotiate->record_size_limit < max_len) {
        record_size_limit = ssl->session_negotiate->record_size_limit;
    }

    return record_size_limit;
}
```

## Implementation Behavior

The server stores the limit in `session_negotiate`. Application-data writes query it through `mbedtls_ssl_get_max_out_record_payload()`. Protected handshake messages instead follow `mbedtls_ssl_tls13_write_certificate()` to `mbedtls_ssl_finish_handshake_msg()`, then to record encryption, with only `MBEDTLS_SSL_OUT_CONTENT_LEN` enforced. A sufficiently large Certificate or CertificateVerify can therefore become one protected record above the peer's negotiated maximum.

## Inconsistency Reason

RFC 8449 prohibits generating any protected record whose plaintext exceeds the received limit, and RFC 8446 applies the reduced bound to the full inner plaintext. mbedTLS received and stored `513` but emitted a protected handshake plaintext of `848`. This is not a boundary-interpretation dispute; it is a direct violation of the negotiated output constraint.

## Runtime Evidence

The test used an mbedTLS TLS 1.3 server built with `MBEDTLS_SSL_RECORD_SIZE_LIMIT` and a `gnutls-cli --recordsize 512` client. The client advertisement was decoded by mbedTLS as `RecordSizeLimit: 513 Bytes`. The server sent EncryptedExtensions, confirming that protected handshake traffic had begun, and then constructed a larger protected handshake message.

The server observed:

```text
ClientHello: record_size_limit(28) extension received.
RecordSizeLimit: 513 Bytes
EncryptedExtensions: record_size_limit(28) extension exists.
before encrypt: msglen = 848, including 0 bytes of padding
output record: msgtype = 23, version = [3:3], msglen = 864
message length: 869, out_left: 869
```

The client observed:

```text
ENCRYPTED EXTENSIONS (8) was received.
record_size_limit 16384 negotiated
Received 864 bytes, while expecting less than 831
*** Fatal error: Decryption has failed.
```

The test process completed as designed, while the client handshake exited with failure status `1`. The sequence demonstrates that the server received the smaller peer limit, entered protected-handshake transmission, emitted an over-limit record, and was immediately rejected by the peer.

## Impact

- Peers advertising a small `record_size_limit` can fail TLS 1.3 certificate handshakes, especially with larger Certificate or CertificateVerify messages.
- The failure occurs before connection establishment rather than only during application data.
- The issue is gated by `MBEDTLS_SSL_RECORD_SIZE_LIMIT`, but enabled builds violate RFC 8449 for protected handshake records.

## Fix Direction

- Apply the negotiated limit to TLS 1.3 protected handshake output, not only application data.
- Compute per-record capacity from `mbedtls_ssl_get_output_record_size_limit()` while reserving TLS 1.3 inner content-type and padding overhead.
- Add record-level fragmentation for stream-TLS handshake messages, or split large Certificate and CertificateVerify messages before encryption.
- Add a TLS 1.3 certificate-handshake regression with a small peer limit and assert that every protected record stays within the limit and the handshake completes.
