# Confirmed issue in keeping the full encoded TLSInnerPlaintext at or below 2^14 + 1 octets

## Problem Description

This is a real TLS 1.3 issue.

The stream-TLS handshake path can build a protected handshake record whose plaintext content is exactly 16384 bytes, and the TLS 1.3 record wrapper then appends the inner `ContentType` plus 15 bytes of zero padding. That produces an encoded `TLSInnerPlaintext` of 16400 bytes, which exceeds the RFC 8446 limit of `2^14 + 1 = 16385`.

I re-checked the standard context and then ran a dedicated local reproducer against the actual mbedTLS TLS 1.3 wrapping code. The runtime result confirms the boundary violation.

This report deduplicates multiple candidate-level records that resolved to the same root cause.

## Standard Requirement

- Official standard: [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html)

- Sections:
  - Section 5.2 Record Payload Protection
  - Section 5.4 Record Padding

Relevant RFC text:

> struct {
>     opaque content[TLSPlaintext.length];
>     ContentType type;
>     uint8 zeros[length_of_padding];
> } TLSInnerPlaintext;

This is the encrypted-record plaintext format for TLS 1.3, including handshake records after record protection starts.

> content:  The TLSPlaintext.fragment value, containing the byte
>    encoding of a handshake or an alert message, or the raw bytes of
>    the application's data to send.

So the `TLSInnerPlaintext` construction explicitly applies to encrypted handshake messages as well as alerts and application data.

> The presence of padding does not change the overall record size
> limitations: the full encoded TLSInnerPlaintext MUST NOT exceed 2^14
> + 1 octets.

Interpretation:

The implementation must ensure that any protected TLS 1.3 record, including protected handshake records, is encoded as a `TLSInnerPlaintext` of length at most 16385 bytes. This bound includes the inner content type and any zero padding.

Reachability under the RFC is not speculative. Section 4.4.2 defines `CertificateEntry.cert_data<1..2^24-1>`, so a `Certificate` message large enough to hit this boundary is standards-compliant and must be handled correctly.

Interpretation:

- `cert_len=16370` is the largest still-compliant case: the handshake record content is 16383 and the wrapped `TLSInnerPlaintext` becomes 16384.
- `cert_len=16371` is the critical boundary case: the handshake record content is 16384 and the wrapped `TLSInnerPlaintext` becomes 16400.
- `cert_len=16372` no longer fits in the handshake message construction buffer and is rejected before wrapping.

The `encrypt_ret=-27648` value is `MBEDTLS_ERR_SSL_INTERNAL_ERROR` from the intentionally incomplete dummy transform used by the probe. That does not weaken the result: the important fact is that `mbedtls_ssl_encrypt_buf()` already mutated `wrapped_len` to 16400 before that later failure point. The actual TLS 1.3 inner-plaintext wrapping logic therefore exceeds the RFC size limit on a reachable boundary input.

## Inconsistency Reason

- RFC 8446 Section 5.2 makes `TLSInnerPlaintext` the cleartext format for encrypted handshake records.
- RFC 8446 Section 5.4 caps the full encoded `TLSInnerPlaintext` at 16385 bytes, including content type and padding.
- mbedTLS allows the handshake layer to reach 16384 bytes of record content.
- The TLS 1.3 wrapper then appends one content-type byte and 15 padding bytes, producing 16400 bytes.

That is a direct standards violation.

## Decision Reason

- The standard text unambiguously applies the `TLSInnerPlaintext` size limit to encrypted handshake records.
- The relevant code paths permit a one-certificate TLS 1.3 `Certificate` message to reach the 16384-byte handshake-record boundary.
- An actual local run of the real wrapping function confirmed that this boundary case is transformed into a 16400-byte `TLSInnerPlaintext`.

The correct verdict is therefore `issue_found`, not `suspected_issue`.

## Remaining Uncertainty

- No material uncertainty remains about the core TLS 1.3 size-limit violation.
- This issue does overlap operationally with the separate stream-TLS handshake-fragmentation defect, because fragmentation could avoid this boundary in practice. However, even without that separate fix, the TLS 1.3 wrapping code itself is already demonstrably willing to construct an oversized `TLSInnerPlaintext`.
