# Zero-length Alert Inner Content Is Mapped to INVALID_RECORD Instead of `unexpected_message`

## Summary

This report confirms a TLS 1.3 receive-side mismatch in the handling of an
Alert record whose `TLSInnerPlaintext.content` is zero-length. RFC 8446
Section 5.4 requires the receiver to terminate the connection with an
`unexpected_message` alert. The current implementation instead returns
`MBEDTLS_ERR_SSL_INVALID_RECORD` and leaves no pending alert to send. A
focused runtime probe was rerun on `2026-08-04` and reproduced the behavior.

## Standard Requirement

- Standard: [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446)
- Section: `5.4 Record Padding`

```text
Application Data records may contain a zero-length
TLSInnerPlaintext.content if the sender desires.  This permits
generation of plausibly sized cover traffic in contexts where the
presence or absence of activity may be sensitive.  Implementations
MUST NOT send Handshake and Alert records that have a zero-length
TLSInnerPlaintext.content; if such a message is received, the
receiving implementation MUST terminate the connection with an
"unexpected_message" alert.
```

This rule makes an explicit distinction between `Alert` and
`Application Data`: zero-length inner content is only allowed for
`Application Data`. Once a TLS 1.3 receiver reconstructs an inner plaintext
whose type is `Alert` and whose content length is `0`, it must terminate the
connection with `unexpected_message`.

## Relevant Source Code

### `library/ssl_msg.c:496-511`

```c
static int ssl_parse_inner_plaintext(unsigned char const *content,
                                     size_t *content_size,
                                     uint8_t *rec_type)
{
    size_t remaining = *content_size;

    do {
        if (remaining == 0) {
            return -1;
        }
        remaining--;
    } while (content[remaining] == 0);

    *content_size = remaining;
    *rec_type = content[remaining];
```

If the decrypted inner plaintext consists of a single non-zero `ContentType`
byte and no preceding content bytes, this logic sets `*rec_type` to that type
and sets `*content_size` to `0`.

### `library/ssl_msg.c:4899-4904`

```c
    /* The record content type may change during decryption,
     * so re-read it. */
    ssl->in_msgtype = rec.type;

    ssl->in_msg    = rec.buf + rec.data_offset;
    ssl->in_msglen = rec.data_len;
```

After TLS 1.3 decryption, the reconstructed inner type and inner content
length are written back to `ssl->in_msgtype` and `ssl->in_msglen`. As a
result, a zero-length inner Alert enters the alert-processing path with
`in_msglen == 0`.

### `library/ssl_msg.c:4970-4977`

```c
    if (ssl->in_msgtype == MBEDTLS_SSL_MSG_ALERT) {
        if (ssl->in_msglen != 2) {
            /* Note: Standard allows for more than one 2 byte alert
               to be packed in a single message, but Mbed TLS doesn't
               currently support this. */
            MBEDTLS_SSL_DEBUG_MSG(1, ("invalid alert message, len: %" MBEDTLS_PRINTF_SIZET,
                                      ssl->in_msglen));
            return MBEDTLS_ERR_SSL_INVALID_RECORD;
        }
```

Once the reconstructed Alert reaches the message-type handler with
`in_msglen == 0`, it is rejected as a generic
`MBEDTLS_ERR_SSL_INVALID_RECORD` instead of being mapped to
`unexpected_message`.

### `library/ssl_msg.c:4877-4885`

```c
            /* Error out (and send alert) on invalid records */
#if defined(MBEDTLS_SSL_ALL_ALERT_MESSAGES)
            if (ret == MBEDTLS_ERR_SSL_INVALID_MAC) {
                mbedtls_ssl_send_alert_message(ssl,
                                               MBEDTLS_SSL_ALERT_LEVEL_FATAL,
                                               MBEDTLS_SSL_ALERT_MSG_BAD_RECORD_MAC);
            }
#endif
            return ret;
```

The generic invalid-record path only auto-sends an alert for
`MBEDTLS_ERR_SSL_INVALID_MAC`. The zero-length inner Alert path returns
`MBEDTLS_ERR_SSL_INVALID_RECORD`, so no outbound `unexpected_message` alert is
scheduled automatically.

## Implementation Behavior

1. After AEAD success, the TLS 1.3 receive path reconstructs the true inner
   `ContentType` and inner content length from `TLSInnerPlaintext`.
2. If the decrypted record contains only an `Alert` type byte and no content
   bytes, the parsed state becomes `in_msgtype = MBEDTLS_SSL_MSG_ALERT` and
   `in_msglen = 0`.
3. The alert handler requires a 2-byte Alert payload and rejects this case as
   `MBEDTLS_ERR_SSL_INVALID_RECORD`.
4. This error path does not pend `unexpected_message`, so the outer layer does
   not send the RFC-mandated fatal alert to the peer.

## Inconsistency Reason

RFC 8446 Section 5.4 assigns a specific protocol error for zero-length Alert
inner content: the connection must be terminated with `unexpected_message`.
The current implementation does terminate processing, but it does so by
returning a generic local `INVALID_RECORD` error and by scheduling no
corresponding TLS alert. The externally observable behavior therefore does not
match the standard.

## Impact

- The peer does not observe the RFC 8446-mandated `unexpected_message` alert.
- TLS 1.3 negative conformance and interoperability tests observe the wrong
  failure semantics.
- Debugging and auditing lose precision because this condition is collapsed
  into a generic `INVALID_RECORD`.

## Fix Direction

- Add a dedicated receive-side check after TLS 1.3 inner-plaintext
  reconstruction for the case `Alert` with `in_msglen == 0`.
- Pend and send `MBEDTLS_SSL_ALERT_MSG_UNEXPECTED_MESSAGE` before returning
  the local error.
- Keep the fix scoped to TLS 1.3 inner-plaintext semantics so that unrelated
  malformed-alert handling is not changed accidentally.
