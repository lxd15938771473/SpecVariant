# Zero-length Handshake Inner Content Is Mapped to INVALID_RECORD Instead of `unexpected_message`

## Summary

This report confirms a TLS 1.3 receive-side mismatch in the handling of a Handshake record whose `TLSInnerPlaintext.content` is zero-length. RFC 8446 Section 5.4 requires the receiver to terminate the connection with an `unexpected_message` alert. The current implementation instead returns `MBEDTLS_ERR_SSL_INVALID_RECORD` and leaves no pending alert to send. A focused runtime probe executed on `2026-08-04` reproduced the behavior.

## Standard Requirement

- Standard: [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446)
- Section: `5.4 Record Padding`

```text
Application Data records may contain a zero-length
TLSInnerPlaintext.content if the sender desires.  This permits
generation of plausibly sized cover traffic in contexts where the
presence or absence of activity may be sensitive.  Implementations
MUST NOT send Handshake and Alert records that have a zero-length
TLSInnerPlaintext.content; if such a message is received, the
receiving implementation MUST terminate the connection with an
"unexpected_message" alert.
```

This rule makes an explicit distinction between `Handshake` and `Application Data`: zero-length inner content is only allowed for `Application Data`. Once a TLS 1.3 receiver reconstructs an inner plaintext whose type is `Handshake` and whose content length is `0`, it must terminate the connection with `unexpected_message`.

## Relevant Source Code

### `library/ssl_msg.c:496-511`

```c
static int ssl_parse_inner_plaintext(unsigned char const *content,
                                     size_t *content_size,
                                     uint8_t *rec_type)
{
    size_t remaining = *content_size;

    do {
        if (remaining == 0) {
            return -1;
        }
        remaining--;
    } while (content[remaining] == 0);

    *content_size = remaining;
    *rec_type = content[remaining];
```

If the decrypted inner plaintext consists of a single non-zero `ContentType` byte and no preceding content bytes, this logic sets `*rec_type` to that type and sets `*content_size` to `0`.

### `library/ssl_msg.c:4899-4904`

```c
    /* The record content type may change during decryption,
     * so re-read it. */
    ssl->in_msgtype = rec.type;

    ssl->in_msg    = rec.buf + rec.data_offset;

```

After TLS 1.3 decryption, the reconstructed inner type and inner content length are written back to `ssl->in_msgtype` and `ssl->in_msglen`. As a result, a zero-length inner Handshake enters the handshake-processing path with `in_msglen == 0`.

### `library/ssl_msg.c:2931-2942`

```c

{
    if (ssl->in_hsfraglen == 0) {

```

When `in_msglen == 0`, the handshake preparser treats the record as too short to contain a handshake header and returns `MBEDTLS_ERR_SSL_INVALID_RECORD`.

### `library/ssl_tls.c:4262-4268`

```c

        if (ssl->send_alert) {
            ret = mbedtls_ssl_handle_pending_alert(ssl);
```

The outer layer only sends a fatal alert when `ssl->send_alert` has already been set. The zero-length Handshake path above does not pend `unexpected_message`, so the required alert is never sent automatically.

## Implementation Behavior

1. The TLS 1.3 receive path parses `TLSInnerPlaintext` after AEAD success and reconstructs the true inner `ContentType` and inner content length.
2. When the decrypted result contains only a `Handshake` type byte and no content bytes, the parsed state becomes `in_msgtype = MBEDTLS_SSL_MSG_HANDSHAKE` and `in_msglen = 0`.
3. The handshake preparser requires at least the 4-byte handshake header, so it rejects the record as `MBEDTLS_ERR_SSL_INVALID_RECORD`.
4. This error path does not pend `unexpected_message`, so the outer layer does not send the RFC-mandated fatal alert to the peer.

## Inconsistency Reason

RFC 8446 Section 5.4 assigns a specific protocol error for zero-length Handshake inner content: the connection must be terminated with `unexpected_message`. The current implementation does terminate processing, but it does so by returning a generic local `INVALID_RECORD` error and by scheduling no corresponding TLS alert. The externally observable behavior therefore does not match the standard.

## Impact

- The peer does not observe the RFC 8446-mandated `unexpected_message` alert.
- TLS 1.3 negative conformance and interoperability tests observe the wrong failure semantics.
- Debugging and auditing lose precision because this condition is collapsed into a generic `INVALID_RECORD`.

## Fix Direction

- Add a dedicated receive-side check after TLS 1.3 inner-plaintext reconstruction for the case `Handshake` with `in_msglen == 0`.
- Pend and send `MBEDTLS_SSL_ALERT_MSG_UNEXPECTED_MESSAGE` before returning the local error.
- Keep the fix scoped to TLS 1.3 inner-plaintext semantics so that unrelated short-handshake-message handling is not changed accidentally.
