# Mbed TLS does not implement the TLS 1.3 `signature_algorithms_cert` extension

## Problem Description

This is a real TLS 1.3 standards-compliance gap, but the original report title
was too narrow.

RFC 8446 does **not** require every TLS 1.3 ClientHello or CertificateRequest
to carry `signature_algorithms_cert`. Section 4.2.3 explicitly says that if an
implementation uses the same policy for TLS signatures and certificate
signatures, it **MAY omit** the extension.

The confirmed issue is broader: Mbed TLS does not implement the TLS 1.3
`signature_algorithms_cert` extension itself. The recheck confirms that:

- the extension is registered in shared tables and allowed-extension masks;
- actual TLS 1.3 client and server paths only implement
  `signature_algorithms`;
- the real TLS 1.3 client omits extension `50` on the wire;
- the real TLS 1.3 server, even on a successful client-authenticated
  handshake, emits `signature_algorithms` in `CertificateRequest` but not
  `signature_algorithms_cert`;
- Mbed TLS's own TLS 1.3 support matrix documents
  `signature_algorithms_cert` as unsupported.

This makes the correct issue statement "missing implementation of the TLS 1.3
`signature_algorithms_cert` extension", not merely "one observed ClientHello
omitted it".

## Standard Requirement

- Official standard: [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html)

- Sections: `Section 4.2.3 Signature Algorithms` and
  `Section 9.2 Mandatory-to-Implement Extensions`

Section 4.2.3 defines the meaning and omission rule:

```text
The "signature_algorithms_cert" extension applies to signatures in
certificates, and the "signature_algorithms" extension ... applies to
signatures in CertificateVerify messages.

If no "signature_algorithms_cert" extension is present, then the
"signature_algorithms" extension also applies to signatures appearing in
certificates.

Implementations which have the same policy in both cases MAY omit the
"signature_algorithms_cert" extension.
```

Section 9.2 then lists the extension as mandatory to implement:

```text
In the absence of an application profile standard specifying otherwise, a
TLS-compliant application MUST implement the following TLS extensions:

-  Supported Versions ("supported_versions"; Section 4.2.1)
-  Cookie ("cookie"; Section 4.2.2)
-  Signature Algorithms ("signature_algorithms"; Section 4.2.3)
-  Signature Algorithms Certificate ("signature_algorithms_cert";
   Section 4.2.3)
```

Interpretation:

RFC 8446 allows an implementation to omit `signature_algorithms_cert` from a
particular handshake when the certificate-signature policy is identical to the
ordinary TLS signature policy. However, that omission rule does not waive the
separate Section 9.2 requirement to implement the extension. A TLS 1.3 stack
that only falls back to `signature_algorithms` and never provides a
`signature_algorithms_cert` parsing or generation path is not fully compliant.

## Relevant Source Code And Documentation

### Registration exists, but registration alone is not implementation

#### `library/ssl_tls.c:576-577`, `library/ssl_tls.c:633`, `library/ssl_tls.c:665`

Mbed TLS assigns an internal extension ID, name, and numeric mapping for
`signature_algorithms_cert`.

#### `library/ssl_misc.h:155` and `library/ssl_misc.h:179`

The allowed-extension masks include `SIG_ALG_CERT` for TLS 1.3 ClientHello and
CertificateRequest handling.

These entries show awareness of extension `50`, but they do not provide a real
TLS 1.3 parser, serializer, or policy-application path.

### The actual TLS 1.3 ClientHello path only writes `signature_algorithms`

#### `library/ssl_client.c:639-655`

When certificate-based TLS handshakes are enabled, the client-side extension
writer calls `mbedtls_ssl_write_sig_alg_ext(...)`. There is no parallel
`signature_algorithms_cert` writer in this path.

### The actual TLS 1.3 ClientHello parser only handles extension `13`

#### `library/ssl_tls13_server.c:1627-1637`

The server-side TLS 1.3 ClientHello parser has a branch for
`MBEDTLS_TLS_EXT_SIG_ALG` and calls `mbedtls_ssl_parse_sig_alg_ext(...)`. There
is no corresponding `case MBEDTLS_TLS_EXT_SIG_ALG_CERT`.

### The actual TLS 1.3 CertificateRequest parser only handles extension `13`

#### `library/ssl_tls13_client.c:2478-2495`

The client-side TLS 1.3 `CertificateRequest` parser accepts
`MBEDTLS_TLS_EXT_SIG_ALG` and ignores unhandled extensions by default. There is
no `signature_algorithms_cert` parse branch.

### The actual TLS 1.3 CertificateRequest writer only writes extension `13`

#### `library/ssl_tls13_server.c:2715-2729`

The server-side TLS 1.3 `CertificateRequest` writer explicitly says that the
extensions must contain `signature_algorithms`, then calls
`mbedtls_ssl_write_sig_alg_ext(...)`. No `signature_algorithms_cert` writer is
invoked before printing the final sent-extension mask.

### Project documentation also marks the extension unsupported

#### `docs/architecture/tls13-support.md:34-58`

Mbed TLS's own TLS 1.3 support matrix lists:

```text
| signature_algorithms         | YES     |
| ...
| signature_algorithms_cert    | no      |
```

This matches the code review: the extension is not just omitted in one run, it
is documented as unsupported.

## Runtime Evidence

### Round 1

- Status: `completed`
- Positive control: `run`
- Reproducer: `run`


Observed behavior:

- The control handshake completed successfully over TLS 1.3.
- The captured first ClientHello advertised extension IDs
  `0x0000`, `0x002b`, `0x0033`, `0x002d`, `0x000a`, and `0x000d`.
- The parsed result was `signature_algorithms_cert_present: false`.

Runtime interpretation:

This confirms that the audited client build does not send extension `50` on its
real TLS 1.3 ClientHello. By itself, that would not yet prove a compliance
issue, because RFC 8446 allows omission when both policies are the same.

### Round 2

- Status: `completed`
- Positive control: `run`
- Reproducer: `run`

- Server:
  `ssl_server2.exe` with TLS 1.3 and required client authentication
- Client:
  `ssl_client2.exe` with TLS 1.3 on loopback

Observed behavior:

- The client-authenticated TLS 1.3 handshake completed successfully.
- The server log shows a real TLS 1.3 ClientHello parse with:
  - `ClientHello: signature_algorithms(13) extension exists.`
  - `ClientHello: signature_algorithms_cert(50) extension does not exist.`
- The same server log later shows a real TLS 1.3 `CertificateRequest` write
  path:
  - `adding signature_algorithms extension`
  - `CertificateRequest: signature_algorithms(13) extension exists.`
  - `CertificateRequest: signature_algorithms_cert(50) extension does not exist.`
- Both peers report `[ Protocol is TLSv1.3 ]`.

Runtime interpretation:

This round is more important than Round 1 because it reaches the role where
`signature_algorithms_cert` is actually relevant: a certificate-authenticated
TLS 1.3 handshake with a server-generated `CertificateRequest`. The server
really emits `signature_algorithms`, but the same successful runtime path shows
no `signature_algorithms_cert` extension being emitted.

Again, omission in one successful handshake could still be allowed by RFC
policy equivalence. However, when combined with the static evidence that there
is no TLS 1.3 `signature_algorithms_cert` writer or parser, this runtime check
confirms there is no hidden implementation path in the audited build.

## Decision Reason

The final verdict is `issue_found` for the following combined reason:

- RFC 8446 Section 4.2.3 allows omission of `signature_algorithms_cert` in a
  given handshake, so message omission alone is not sufficient to prove a bug.
- RFC 8446 Section 9.2 separately requires TLS-compliant applications to
  implement `signature_algorithms_cert`.
- The audited Mbed TLS tree has only registration/mask entries for extension
  `50`, but no TLS 1.3 ClientHello parser branch, no TLS 1.3
  `CertificateRequest` parser branch, and no TLS 1.3
  `CertificateRequest` writer for `signature_algorithms_cert`.
- Mbed TLS's own support matrix explicitly marks
  `signature_algorithms_cert` as unsupported.
- Focused runtime evidence confirms the real client omits extension `50`, and
  the real client-authenticated server handshake emits `signature_algorithms`
  without any hidden `signature_algorithms_cert` path.

Therefore, the real issue is a missing TLS 1.3 implementation of
`signature_algorithms_cert`, not just a missing field in one observed
ClientHello.

## Remaining Uncertainty

None that affects the verdict.

The only nuance is the standards boundary: RFC 8446 does not require this
extension to appear in every handshake. The confirmed defect is not
"omitted once on the wire", but "not implemented as a TLS 1.3 extension at
all in the audited build".
