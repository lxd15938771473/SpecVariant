# Confirmed missing `decode_error` on nonzero malformed Alert records

## Problem Description

This is a real TLS 1.3 issue, but the confirmed trigger is narrower than the earlier report text.

I re-ran the check on 2026-08-06 with a dedicated local probe compiled against
the current source tree. The earlier zero-length-only probe is no longer used
as decisive evidence for this report. After a standards re-check against RFC
9846 and RFC 8446, zero-length encrypted Alert content belongs to the separate
`unexpected_message` requirement tracked by report `0006`.

This report is now confirmed by two nonzero malformed Alert payloads:

- a 1-byte Alert payload that contains only `AlertLevel` and is missing `AlertDescription`
- a 3-byte Alert payload that contains a valid two-byte Alert plus trailing garbage

In both cases, Mbed TLS returns `MBEDTLS_ERR_SSL_INVALID_RECORD` without pending or sending the required fatal `decode_error` alert.

## Standard Requirement

- Official standards: [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html) and [RFC 9846](https://www.rfc-editor.org/rfc/rfc9846.html)

- Sections:
  - Section 5.1 Record Layer
  - Section 5.4 Record Padding
  - Section 6 Alert Protocol

Relevant RFC text:

> Alert messages (Section 6) MUST NOT be fragmented across records, and
> multiple alert messages MUST NOT be coalesced into a single
> TLSPlaintext record. In other words, a record with an Alert type
> MUST contain exactly one message.

> struct {
>     AlertLevel level;
>     AlertDescription description;
> } Alert;

> Peers which receive a message which cannot be parsed according to the syntax
> ... MUST terminate the connection with a "decode_error" alert.

> Implementations MUST NOT send Handshake and Alert records that have a
> zero-length TLSInnerPlaintext.content; if such a message is received, the
> receiving implementation MUST terminate the connection with an
> "unexpected_message" alert.

Interpretation:

- A decrypted Alert payload of 1 byte or 3 bytes is a syntax-invalid encoding of the fixed two-byte `Alert` structure, so the receiver must terminate with fatal `decode_error`.
- A decrypted Alert payload of 0 bytes is controlled by the more specific zero-length rule and must terminate with fatal `unexpected_message`.
- Therefore, zero length is not valid confirming evidence for this report. The confirmed `decode_error` issue in `0019` must be anchored to nonzero malformed Alert lengths instead.

A standards re-check on `2026-08-06` confirmed this distinction between the
specific zero-length rule and the generic malformed nonzero-length rule.

All non-2-byte inbound Alert payloads collapse into a plain `MBEDTLS_ERR_SSL_INVALID_RECORD` return. This path does not pend a fatal alert, so later layers have nothing to send.

This contrast matters: other syntax-boundary failures do explicitly pend `decode_error`.

### `library/ssl_msg.c:6236-6259`

```c
int mbedtls_ssl_handle_pending_alert(mbedtls_ssl_context *ssl)
{
    int ret;

    /* No pending alert, return success*/
    if (ssl->send_alert == 0) {
        return 0;
    }

    ret = mbedtls_ssl_send_alert_message(ssl,
                                         MBEDTLS_SSL_ALERT_LEVEL_FATAL,
                                         ssl->alert_type);
```

Fatal alerts are emitted only if a lower parsing path has already set `ssl->send_alert`.

## Inconsistency Reason

- For malformed inbound TLS 1.3 Alert payloads of 1 byte or 3 bytes, the reviewed tree returns `MBEDTLS_ERR_SSL_INVALID_RECORD` with no pending fatal alert instead of terminating with fatal `decode_error`.

## Decision Reason

- The standards re-check on 2026-08-06 confirms the split cleanly: zero-length Alert content belongs to `unexpected_message`, while 1-byte and 3-byte Alert payloads require `decode_error`.
- The dedicated local probe confirms that the current Mbed TLS tree handles both nonzero malformed cases with the same `INVALID_RECORD`/no-alert behavior.
- That is enough to keep `0019` confirmed, but only after narrowing its confirmed trigger to nonzero malformed Alert lengths.

## Remaining Uncertainty

- None for the 1-byte and 3-byte malformed Alert triggers described above.
- Zero-length Alert content is intentionally out of scope for this report and should be handled under report `0006`.
