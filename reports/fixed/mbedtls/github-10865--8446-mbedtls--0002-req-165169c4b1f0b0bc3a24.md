# TLS 1.3 Server Accepts an Oversized `supported_versions` Vector in ClientHello

## Summary

This is a confirmed server-side parsing issue, not a client encoding defect. After receiving a mutated ClientHello with `supported_versions.versions_len = 255`, the mbedTLS server sent ServerHello instead of rejecting the syntactically invalid vector during parsing.

## Standard Requirement

- [RFC 8446 Section 4.2.1, Supported Versions](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.2.1)
- [RFC 8446 Section 3.4, Vectors](https://www.rfc-editor.org/rfc/rfc8446.html#section-3.4)
- [RFC 8446 Section 6, `decode_error`](https://www.rfc-editor.org/rfc/rfc8446.html#section-6)

```text
uint16 ProtocolVersion;

Variable-length vectors are defined by specifying a subrange of legal
lengths, inclusively, using the notation <floor..ceiling>.
...
The length of an encoded vector must be an exact multiple of the length
of a single element (e.g., a 17-byte vector of uint16 would be illegal).

case client_hello:
     ProtocolVersion versions<2..254>;
```

```text
decode_error:  A message could not be decoded because some field was
   out of the specified range or the length of the message was
   incorrect.
```

The ClientHello vector must contain `2..254` bytes and, because each `ProtocolVersion` is a `uint16`, its length must be even. A value of `255` violates both constraints and requires a parse-time `decode_error`.

## Relevant Source Code

### `library/ssl_tls13_client.c:45`

```c
unsigned char versions_len = (ssl->handshake->min_tls_version <=
                              MBEDTLS_SSL_VERSION_TLS1_2) ? 4 : 2;

MBEDTLS_PUT_UINT16_BE(MBEDTLS_TLS_EXT_SUPPORTED_VERSIONS, p, 0);
MBEDTLS_PUT_UINT16_BE(versions_len + 1, p, 2);
p += 4;

*p++ = versions_len;

mbedtls_ssl_write_version(p, MBEDTLS_SSL_TRANSPORT_STREAM,
                          MBEDTLS_SSL_VERSION_TLS1_3);
```

The normal client writer emits a legal list length of `2` or `4`. The issue is acceptance of a mutated peer input.

The parser checks buffer availability but not `2 <= versions_len <= 254` or even divisibility by two. It also stops at the first acceptable version, leaving the remaining vector bytes unvalidated.

### `library/ssl_tls13_server.c:1355` and `library/ssl_tls13_generic.c:123`

The outer logic locates the extension and passes its raw data boundaries to `ssl_tls13_parse_supported_versions_ext()`. It does not add the missing vector-range or element-size validation.

## Implementation Behavior

The mutated vector retains `0x0304` as its first version but declares 255 data bytes. The server verifies only that 255 bytes exist, reads the first two, recognizes TLS 1.3, and returns success immediately. It neither validates nor fully consumes the remaining 253 bytes. Handshake processing continues through ServerHello and fails only later after the proxy-induced transcript divergence.

## Inconsistency Reason

RFC 8446 defines an even-length `ProtocolVersion versions<2..254>` vector. mbedTLS checks only memory bounds, not the formal length range or element alignment, and early-exits on a supported value. It therefore treats `versions_len = 255` as successfully parsed instead of emitting `decode_error`.

## Runtime Evidence

A ClientHello mutation probe preserved the original leading version bytes and changed the one-byte vector length to `255`, padding the extension with zeros:

```python
elif mode == "supported_versions_oversize":
    versions = data[1:]
    padding = b"\x00" * (255 - len(versions))
    new_items.append((ext_type, bytes([255]) + versions + padding))
```

The server's observed first response was:

```json
{
  "mode": "supported_versions_oversize",
  "success": true,
  "server_first_record": {
    "content_type": 22,
    "record_length": 122,
    "handshake_type": 2
  },
  "client_exit_code": 1,
  "server_exit_code": 1
}
```

Content type `22` is a handshake record and handshake type `2` is ServerHello. The server therefore accepted the initial malformed ClientHello far enough to respond normally. Both peers later failed with `-0x7180` because the proxy changed only the server-visible transcript; that later failure does not replace the missing parse-time rejection.

## Impact

- The server fails to enforce the RFC 8446 presentation syntax for `supported_versions`.
- Oversized or odd-length version vectors advance to a later handshake stage rather than failing at their true error location.
- The delayed failure obscures diagnostics and harms strict conformance and interoperability testing.

## Fix Direction

1. Reject `versions_len < 2 || versions_len > 254` immediately.
2. Reject `versions_len % 2 != 0` because `ProtocolVersion` is two bytes.
3. Validate that the entire vector is syntactically consumable even after finding a supported version.
4. Use `decode_error` for malformed syntax and reserve `protocol_version` for a valid vector with no negotiable version.

## Notes

This refined report retains the `issue_found` result and identifies the root cause as server acceptance of an oversized ClientHello `supported_versions` vector.
