# TLS 1.3 Client Sends the Wrong Alert When PSK-DHE ServerHello Omits `key_share`

## Summary

This is a confirmed issue with a narrow trigger. The client offers only `psk_dhe_ke` (`tls13_kex_modes=psk_ephemeral`), and the server returns a ServerHello containing `pre_shared_key` but no `key_share`. RFC 8446 requires the client to abort with `illegal_parameter`. mbedTLS instead classifies the response as pure PSK and then aborts with `handshake_failure` because that mode is disabled.

The report does not claim that every ServerHello without `key_share` is invalid. The alert mismatch occurs when the client's offered PSK mode requires that extension.

## Standard Requirement

- [RFC 8446 Section 4.2.9, Pre-Shared Key Exchange Modes](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.2.9)
- [RFC 8446 Section 4.2.11, Pre-Shared Key Extension](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.2.11)

```text
psk_ke:  PSK-only key establishment.  In this mode, the server
   MUST NOT supply a "key_share" value.

psk_dhe_ke:  PSK with (EC)DHE key establishment.  In this mode, the
   client and server MUST supply "key_share" values as described in
   Section 4.2.8.

... at present, this is indicated by the presence of the
"key_share" in the ServerHello.
```

```text
Clients MUST verify that the server's selected_identity is within the
range supplied by the client, that the server selected a cipher suite
indicating a Hash associated with the PSK, and that a server
"key_share" extension is present if required by the ClientHello
"psk_key_exchange_modes" extension.  If these values are not
consistent, the client MUST abort the handshake with an
"illegal_parameter" alert.
```

When the client permits only `psk_dhe_ke`, a ServerHello selecting a PSK must include `key_share`. Missing that required extension is an explicit consistency error mapped to `illegal_parameter`, not a generic negotiation failure.

The presence of only `pre_shared_key` is first interpreted as pure PSK. Because pure PSK is disabled, the generic mode-unsupported path schedules `handshake_failure` rather than recognizing the RFC-defined consistency error.

## Implementation Behavior

The client advertises only PSK-ECDHE. A ServerHello containing `pre_shared_key` without `key_share` contradicts that offer, but mbedTLS does not check the relationship at that point. It infers pure PSK from the received extension combination, finds that local mode disabled, and returns the generic `handshake_failure`. The handshake is rejected, but with the wrong peer-visible reason.

## Inconsistency Reason

Sections 4.2.9 and 4.2.11 require `key_share` when ClientHello offered only `psk_dhe_ke` and prescribe `illegal_parameter` for inconsistency. mbedTLS converts the missing extension into a locally unsupported pure-PSK selection and sends `handshake_failure`. The defect is alert mapping and classification, not failure to reject the handshake.

## Runtime Evidence

A C harness linked the real mbedTLS static libraries and invoked the production `ssl_tls13_postprocess_server_hello()` path. It configured the client to allow only `psk_ephemeral` and set `received_extensions` to represent a ServerHello with `pre_shared_key` but no `key_share`.

The observed result was:

```json
{"ret":-28160,"send_alert":1,"alert_type":40,"alert_reason":-28160,"key_exchange_mode":1}
```

`-28160` is `MBEDTLS_ERR_SSL_HANDSHAKE_FAILURE`; `send_alert=1` confirms a fatal alert was scheduled; alert type `40` is `handshake_failure`; and key-exchange mode `1` is `MBEDTLS_SSL_TLS1_3_KEY_EXCHANGE_MODE_PSK`. The execution therefore reproduces the exact disputed transition: the missing required share is classified as pure PSK and mapped to alert 40 instead of `illegal_parameter` 47.

## Impact

- A malformed PSK-DHE ServerHello receives the wrong TLS 1.3 error classification.
- Protocol tests, interoperability debugging, and failure attribution observe a generic negotiation error rather than the required field-consistency error.
- If the client also permits pure PSK, absence of `key_share` may be valid; the issue is limited to offers that require PSK-DHE.

## Fix Direction

1. In `ssl_tls13_postprocess_server_hello()`, validate the received extension combination against the modes advertised in ClientHello before inferring a usable key-exchange mode.
2. If ServerHello selects a PSK without `key_share` and the client did not offer pure PSK, schedule `illegal_parameter`.
3. Preserve the existing correct `illegal_parameter` handling for selected-identity range and PSK-hash mismatches.

## Scope Note

This report covers only a client that requires `psk_dhe_ke`. Its classification is `wrong error/reason-code mapping under malformed PSK-DHE ServerHello`.
