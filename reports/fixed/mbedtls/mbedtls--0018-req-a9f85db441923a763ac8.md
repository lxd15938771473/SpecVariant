# TLS 1.3 Client Sends the Wrong Alert When Rejecting Legacy-Version Negotiation

## Summary

When a TLS 1.3 client receives a ServerHello that negotiates TLS 1.2 or earlier and that version is unacceptable, RFC 8446 requires `protocol_version`. The mbedTLS TLS 1.3 legacy-fallback rejection path sends `illegal_parameter` instead.

Two cases must remain distinct. A ServerHello without `supported_versions` represents legacy-version negotiation. A TLS 1.3-style ServerHello that contains `supported_versions` with an unoffered or pre-TLS-1.3 value has a malformed extension semantic. RFC 8446 requires different alerts; the confirmed issue exists only in the first case.

## Standard Requirement

- [RFC 8446 Appendix D.1, Negotiating with an Older Server](https://www.rfc-editor.org/rfc/rfc8446.html#appendix-D.1)
- [RFC 8446 Section 4.2.1, Supported Versions](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.2.1)

Appendix D.1 requires a TLS 1.3 client to abort with `protocol_version` when a ServerHello negotiates TLS 1.2 or earlier and that version is unsupported or otherwise unacceptable. Such a legacy ServerHello does not contain `supported_versions`.

Section 4.2.1 separately requires `illegal_parameter` if a ServerHello does contain `supported_versions` but selects a version the client did not offer or a version earlier than TLS 1.3. Therefore:

- A TLS 1.3-style ServerHello with `supported_versions=0x0303` requires `illegal_parameter`.
- Rejection of a legacy ServerHello without `supported_versions` requires `protocol_version`.

## Relevant Source Code

### `library/ssl_tls13_client.c:1444`

```c
static int ssl_tls13_preprocess_server_hello(mbedtls_ssl_context *ssl,
                                             const unsigned char *buf,
                                             const unsigned char *end)
{
    int ret = MBEDTLS_ERR_ERROR_CORRUPTION_DETECTED;
    mbedtls_ssl_handshake_params *handshake = ssl->handshake;

    MBEDTLS_SSL_PROC_CHK_NEG(ssl_tls13_is_supported_versions_ext_present(
                                 ssl, buf, end));

    if (ret == 0) {
        MBEDTLS_SSL_PROC_CHK_NEG(
            ssl_tls13_is_downgrade_negotiation(ssl, buf, end));

        if (handshake->min_tls_version > MBEDTLS_SSL_VERSION_TLS1_2 || ret) {
            MBEDTLS_SSL_PEND_FATAL_ALERT(MBEDTLS_SSL_ALERT_MSG_ILLEGAL_PARAMETER,
                                         MBEDTLS_ERR_SSL_ILLEGAL_PARAMETER);
            return MBEDTLS_ERR_SSL_ILLEGAL_PARAMETER;
        }

        ssl->keep_current_message = 1;
        ssl->tls_version = MBEDTLS_SSL_VERSION_TLS1_2;
        /* ... */
        return SSL_SERVER_HELLO_TLS1_2;
    }
```

`ssl_tls13_is_supported_versions_ext_present()` returns `0` when the extension is absent, entering the legacy-negotiation branch. For a TLS-1.3-only client, `handshake->min_tls_version > MBEDTLS_SSL_VERSION_TLS1_2` is true, and the implementation schedules `ILLEGAL_PARAMETER`. The helper's absent-extension behavior is at `library/ssl_tls13_client.c:1332`; the configured minimum is copied at `library/ssl_client.c:783`.

This second branch runs only after the message remains on the TLS 1.3 ServerHello parsing path. Sending `illegal_parameter` for a present `supported_versions` value of TLS 1.2 or earlier is correct under Section 4.2.1 and is not evidence of this issue.

## Implementation Behavior

The preprocessing stage recognizes the absence of `supported_versions` as legacy negotiation. If the client policy rejects that negotiated version, it nevertheless schedules `illegal_parameter`. By contrast, the later extension parser also schedules `illegal_parameter` for a present but invalid version value, which is correct. The implementation wrongly uses the extension-semantic alert for the distinct legacy-version rejection path.

## Inconsistency Reason

Appendix D.1 requires `protocol_version` for an unacceptable legacy negotiation, while mbedTLS schedules `illegal_parameter` in `ssl_tls13_preprocess_server_hello()`. The wrong alert is peer-visible and was captured on the wire.

## Runtime Evidence

A positive-control TLS 1.3 client/server handshake completed successfully, confirming that the executables and test environment worked.

For the target case, a probe received a real ClientHello from the TLS-1.3-only mbedTLS client, copied its `legacy_session_id`, and returned a structurally valid TLS 1.2 ServerHello without `supported_versions`. Echoing the session ID avoided an earlier `legacy_session_id_echo` rejection and forced the intended legacy-negotiation preprocessing path. The client returned:

```text
alert record:       1503030002022f
alert description:  47 (illegal_parameter)
RFC-required alert: 70 (protocol_version)
```

A control case returned a TLS 1.3-style ServerHello that explicitly contained `supported_versions=0x0303`. It produced the same wire alert description `47`, which is the RFC-required `illegal_parameter` for that case. This control confirms both that the alert capture is correct and that the later `ssl_tls13_parse_supported_versions_ext()` branch is compliant rather than part of the defect.

## Impact

Peers and conformance tests observe the wrong reason for rejecting legacy-version negotiation. The result conflates an unacceptable negotiated protocol version with a malformed TLS 1.3 extension value.

## Fix Direction

In the absent-`supported_versions` legacy-negotiation rejection branch, schedule `MBEDTLS_SSL_ALERT_MSG_PROTOCOL_VERSION` while retaining `illegal_parameter` for the present-but-invalid `supported_versions` case. Add separate regression tests for both paths.

## Remaining Uncertainty

No material uncertainty remains for a TLS-1.3-only client configured with `force_version=tls13`. This report is limited to Appendix D.1 legacy-version rejection; the malformed `supported_versions` control is compliant.
