# OpenSSL accepts an unrequested delegated_credential extension in TLS 1.3 EncryptedExtensions

## Summary

- Latest runtime check: `2026-08-10`

OpenSSL's stock TLS 1.3 client accepts an unrequested server extension response in `EncryptedExtensions`. The focused reproducer injects extension type `34` (`delegated_credential`) into the TLS 1.3 `EncryptedExtensions` message; OpenSSL completes the handshake instead of aborting with `unsupported_extension`.

The issue is not that OpenSSL implements `delegated_credential` with the wrong placement. Stock OpenSSL does not implement a built-in `delegated_credential` extension. The precise issue is that the TLS 1.3 client path accepts an unknown, unrequested server extension response in `EncryptedExtensions`.

## Standard Requirement

- Standard: [RFC 9846 Section 4.3, `Extensions`](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.3)
- Alert definition: [RFC 9846 Section 6.2, `unsupported_extension`](https://www.rfc-editor.org/rfc/rfc9846.html#section-6.2)
- Extension table row: `delegated_credential [RFC9345]` is allowed in `CH, CR, CT`; it is not allowed in `EE`.

RFC 9846 defines TLS extensions as request/response structured and explicitly identifies `EncryptedExtensions` as a server extension response message:

```text
The client sends its extension requests in the ClientHello message, and the server sends its extension responses in the ServerHello, EncryptedExtensions, HelloRetryRequest, and Certificate messages.
```

It then gives the mandatory behavior for an unrequested response extension:

```text
Implementations MUST NOT send extension responses (i.e., in the ServerHello, EncryptedExtensions, HelloRetryRequest, and Certificate messages) if the remote endpoint did not send the corresponding extension requests, with the exception of the "cookie" extension in the HelloRetryRequest. Upon receiving such an extension, an endpoint MUST abort the handshake with an "unsupported_extension" alert.
```

RFC 9846 also lists where recognized TLS 1.3 extensions may appear. The relevant row is:

```text
| delegated_credential [RFC9345] | CH, CR, CT |
```

Two standard rules can be confused here:

- Unrequested extension responses in `ServerHello`, `EncryptedExtensions`, `HelloRetryRequest`, or `Certificate` require an `unsupported_extension` abort.
- Recognized extensions in a message where they are not specified require an `illegal_parameter` abort.

For OpenSSL's stock behavior, the first rule is decisive. OpenSSL does not recognize extension type `34` as a built-in extension, and the injected extension appears in `EncryptedExtensions`, a server extension response message. The client did not offer `delegated_credential` in the corresponding `ClientHello`, so the receiver should abort with `unsupported_extension`.

The RFC's unknown-extension tolerance does not cover this case. RFC 9846 requires servers to ignore unknown extensions in `ClientHello`, and TLS 1.3 clients to ignore unknown extensions in `CertificateRequest` or `NewSessionTicket`. It does not say that clients may ignore unknown extensions in `EncryptedExtensions`.

## Implementation Behavior

When an unknown extension type appears in TLS 1.3 `EncryptedExtensions`, OpenSSL's client-side parser:

- accepts the extension as unknown,
- skips it during collection,
- does not apply the built-in unrequested-response check,
- continues parsing the remaining handshake,
- completes the TLS 1.3 connection.

For extension type `34`, this means an injected `delegated_credential` extension in `EncryptedExtensions` is accepted even though the extension was not first offered and `delegated_credential` is not listed as valid for `EncryptedExtensions`.

## Inconsistency Reason

RFC 9846 requires an endpoint to abort with `unsupported_extension` when it receives an extension response in `EncryptedExtensions` that was not first offered in the corresponding `ClientHello` or `CertificateRequest`.

OpenSSL instead treats type `34` as an unknown extension and silently skips it in the `EncryptedExtensions` path. The behavior matches OpenSSL's generic unknown-extension tolerance, but that tolerance is too broad for TLS 1.3 server response messages.

The expected behavior is a fatal `unsupported_extension` alert. The observed behavior is successful connection establishment.

## Impact

OpenSSL's TLS 1.3 client is more permissive than RFC 9846 allows for unrequested server extension responses in `EncryptedExtensions`. This weakens protocol conformance checks for extension negotiation and may also affect other unimplemented extension types that appear as unrequested server responses.

## Fix Direction

Add validation for unknown, unrequested extensions in TLS 1.3 server response messages beyond `ServerHello`, especially `EncryptedExtensions` and `Certificate`.

One possible direction is to call `tls_validate_no_unknown_extensions()`, or an equivalent response-extension validation helper, before accepting `EncryptedExtensions`. The implementation should still preserve the RFC-required tolerance for unknown extensions in `ClientHello`, `CertificateRequest`, and `NewSessionTicket`.
