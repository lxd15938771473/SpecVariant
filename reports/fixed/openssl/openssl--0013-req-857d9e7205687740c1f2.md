# TLS 1.3 connection secrets remain nonzero when the connection object is freed

## Summary

OpenSSL derives TLS 1.3 key-schedule and traffic secrets, stores several of them in inline fields of `SSL_CONNECTION`, and clears the transient stack buffers used during derivation. However, the persistent TLS 1.3 secret fields in `SSL_CONNECTION` remain nonzero when `SSL_free()` reaches the allocator free hook for the connection allocation.

This is best framed as a real RFC 9846 secret-erasure issue at `SHOULD` strength, not as a wire-protocol interoperability `MUST` violation. The concrete problem is narrow: per-connection TLS 1.3 secrets persist in the freed connection object instead of being cleansed before `OPENSSL_free(s)`.

## Standard Requirement

Official standard: RFC 9846: <https://www.rfc-editor.org/rfc/rfc9846.html>

RFC 9846 Section 1.1 states that uppercase requirement words are interpreted under BCP 14. Therefore, the following `SHOULD` requirements are normative recommendations: there can be valid exceptions, but an implementation should understand and weigh the security implications before choosing a different course.

Primary normative text: RFC 9846 Section 7.1, "Key Schedule": <https://www.rfc-editor.org/rfc/rfc9846.html#section-7.1>.

```text
Once all the values which are to be derived from a given secret have
been computed, that secret SHOULD be erased.
```

Related normative text: RFC 9846 Section 7.2, "Updating Traffic Secrets": <https://www.rfc-editor.org/rfc/rfc9846.html#section-7.2>.

```text
Once client_/server_application_traffic_secret_N+1 and its associated
traffic keys have been computed, implementations SHOULD delete
client_/server_application_traffic_secret_N and its associated
traffic keys.
```

Security-property context: RFC 9846 Appendix F.1, "Handshake": <https://www.rfc-editor.org/rfc/rfc9846.html#appendix-F.1>.

```text
Forward secret with respect to long-term keys: If the long-term
keying material ... is compromised after the handshake is complete,
this does not compromise the security of the session key ..., as long
as the session key itself (and all material that could be used to
recreate the session key) has been erased.
```

Interpretation: Section 7.1 and Section 7.2 are the direct implementation-facing erasure requirements. Appendix F.1 explains why failing to erase ephemeral or connection-specific secret material can weaken the forward-secrecy property. Appendix F.1's lower-case must be protected phrase should not be converted into a standalone BCP 14 MUST, but it supports treating retained key-schedule material as security-relevant.

The checked RFC 9846 errata did not change the Section 7.1, Section 7.2, or Appendix F.1 secret-erasure text; the reported errata inspected were about version negotiation and deprecation text in other sections.

## Implementation Behavior

Implemented:

- Transient `key` and `secret` buffers in TLS 1.3 derivation and KeyUpdate are cleansed before return.
- Some handshake temporary material, such as `s3.tmp.pms`, uses clear-free paths.
- `SSL_CONNECTION` is initially zero-allocated.

Missing:

- Persistent TLS 1.3 secret arrays embedded in `SSL_CONNECTION` are not cleansed before the connection allocation is freed.
- The free path does not use `OPENSSL_clear_free()` for the full `SSL_CONNECTION` object.
- The free or clear path does not explicitly cleanse `early_secret`, `handshake_secret`, `master_secret`, `resumption_master_secret`, `client_app_traffic_secret`, `server_app_traffic_secret`, or `exporter_master_secret`.

## Inconsistency Reason

RFC 9846 Section 7.1 says key-schedule secrets `SHOULD` be erased once all values derived from them have been computed. Section 7.2 says replaced application traffic secrets and associated traffic keys `SHOULD` be deleted after KeyUpdate. Appendix F.1 explains that forward secrecy depends on erasing the session key and material that can recreate it.

OpenSSL performs some zeroization, so the issue is not a total lack of cleansing. The inconsistency is narrower: secrets that are intentionally retained in `SSL_CONNECTION` during the connection lifetime are still present when the connection object is released. No code path reviewed provides an explicit exception or compensating rationale for leaving these per-connection secrets nonzero at free time.

## Impact

Secret material intended to be ephemeral or connection-specific can remain in released heap memory. A later memory disclosure, allocator reuse exposure, crash dump, or process memory compromise could recover material that RFC 9846 expects implementations to erase for the forward-secrecy property to hold cleanly after the handshake and connection teardown.

Because the governing erasure text is `SHOULD`, the impact should be described as a security-hardening and compliance issue rather than a mandatory protocol-interoperability failure. The security relevance remains concrete because the retained data includes key-schedule material and traffic secrets associated with a completed TLS 1.3 connection.

## Fix Direction

Cleanse persistent TLS 1.3 secret fields before releasing or reinitializing `SSL_CONNECTION`. A direct fix would explicitly cleanse the TLS 1.3 inline secret arrays in the connection free and reset paths before `OPENSSL_free(s)`, or use an equivalent clear-free strategy for the full connection object after subobject ownership has been safely released.

Any fix should preserve the existing transient-buffer cleansing and include a focused regression test that confirms `SSL_free()` clears `early_secret`, `handshake_secret`, `master_secret`, `resumption_master_secret`, `client_app_traffic_secret`, `server_app_traffic_secret`, and `exporter_master_secret` before the connection allocation is released.
