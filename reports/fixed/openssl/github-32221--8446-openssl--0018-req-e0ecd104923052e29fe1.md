# Server may select a certificate chain with an unadvertised certificate signature algorithm

## Summary

OpenSSL provides the checks needed to detect whether a TLS 1.3 certificate chain uses certificate signature algorithms advertised by the client. However, the multi-certificate-chain selection path used by `s_server -xcert` can still select a chain whose CA certificate signature algorithm is not advertised, even when another configured chain is fully compatible.

The issue is confirmed by runtime evidence. In the reproducer, the client advertised only `ecdsa_secp256r1_sha256`. The server had both an ECDSA-signed chain and an RSA/SHA256-signed chain available. OpenSSL reported the first chain as `CA signature: OK` and the second as `CA signature: NOT OK`, but the completed handshake used the second chain.

## Standard Requirement
- Official standard: [RFC 8446, Section 4.2.3, "Signature Algorithms"](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.2.3) and [Section 4.4.2.2, "Server Certificate Selection"](https://www.rfc-editor.org/rfc/rfc8446.html#section-4.4.2.2)

```text
If no "signature_algorithms_cert" extension is present, then the
"signature_algorithms" extension also applies to signatures appearing in
certificates.
```

```text
All certificates provided by the server MUST be signed by a signature
algorithm advertised by the client if it is able to provide such a
chain (see Section 4.2.3).
```

```text
If the server cannot produce a certificate chain that is signed only
via the indicated supported algorithms, then it SHOULD continue the
handshake by sending the client a certificate chain of its choice
that may include algorithms that are not known to be supported by the
client.
```

Interpretation: if the client omits `signature_algorithms_cert`, the regular `signature_algorithms` list still constrains certificate signatures. A fallback chain with unadvertised certificate signature algorithms is allowed only when the server cannot provide a chain signed only with the indicated algorithms. Self-signed certificates and expected trust anchors are excluded from chain validation, but intermediate certificates in the sent chain are not covered by that exception.

### `apps/lib/s_cb.c:1039`

The `s_server -xcert` callback is the runtime path used for multiple configured certificate chains. It calls `SSL_check_chain()` and prints `CA signature`, but it adopts any chain with `CERT_PKEY_VALID`. It does not require `CERT_PKEY_CA_SIGNATURE`, and because it keeps iterating, a later merely-valid chain can replace an earlier fully-compatible chain.

```c
rv = SSL_check_chain(ssl, exc->cert, exc->key, exc->chain);
print_chain_flags(ssl, rv);
if (rv & CERT_PKEY_VALID) {
    if (!SSL_use_certificate(ssl, exc->cert)
        || !SSL_use_PrivateKey(ssl, exc->key)) {
        return 0;
    }
    ...
}
```

## Implementation Behavior

OpenSSL has two relevant behaviors:

1. It can detect whether a candidate chain satisfies the client's certificate signature algorithm constraints. This is visible through `SSL_check_chain()` and the `CERT_PKEY_CA_SIGNATURE` flag.
2. The tested multi-chain selection path does not enforce that flag. It accepts any candidate with `CERT_PKEY_VALID`, so a chain with `CA signature: NOT OK` can still be selected after a chain with `CA signature: OK`.

This is inconsistent with RFC 8446 when the server is able to provide a fully compatible chain. In the runtime test, the server was able to provide such a chain, and OpenSSL identified it, but the final handshake used the incompatible chain.

## Inconsistency Reason

RFC 8446 requires the server to use a chain signed only with advertised algorithms when it can provide one. The OpenSSL path tested here treats `CERT_PKEY_CA_SIGNATURE` as diagnostic information rather than a selection requirement. As a result, `CERT_PKEY_VALID` is sufficient for selection even when another available chain satisfies the stricter certificate-signature requirement.

This is not a case where OpenSSL lacks all support for the rule. The problem is that the available rule is not enforced by the multi-chain selection logic exercised by `s_server -xcert`.

## Runtime Evidence

The test ran an OpenSSL `4.1.0-dev` TLS 1.3 server with two additional P-256 certificate chains. One chain was signed through an ECDSA P-384 root and satisfied the client's sole advertised scheme, `ecdsa_secp256r1_sha256`. The other chain was signed through an RSA/SHA-256 CA and did not satisfy that advertisement. The client then completed one TLS 1.3 connection while the server's certificate-selection diagnostics and the peer certificate were recorded.

Observed output:

```text
Checking cert chain 1:
Subject: CN=P-256 Server Cert
    Overall Validity: OK
    EE signature: OK
    CA signature: OK

Checking cert chain 2:
Subject: CN=P-256 cert EE issuer
    Overall Validity: OK
    EE signature: OK
    CA signature: NOT OK

CONNECTION ESTABLISHED
Protocol version: TLSv1.3
Peer certificate: CN=P-256 cert EE issuer
Signature type: ecdsa_secp256r1_sha256
```

The output proves all required conditions:

- The client offered an ECDSA-only signature algorithm list.
- OpenSSL found a fully compatible available chain.
- OpenSSL also found a second chain whose CA signature did not satisfy the advertised algorithms.
- The completed handshake used the second chain.

## Impact

A TLS 1.3 server using this multi-chain selection path can send a certificate chain containing a CA certificate signature algorithm that the client did not advertise, even though a compatible configured chain is available. This violates the chain-selection requirement in RFC 8446 and may cause interoperability failures with clients that enforce certificate signature algorithm constraints strictly.

## Fix Direction

When selecting among multiple certificate chains for TLS 1.3, the selection logic should prefer a candidate with both `CERT_PKEY_VALID` and `CERT_PKEY_CA_SIGNATURE` when such a candidate exists. Only if no such chain is available should it fall back to a merely valid chain, consistent with RFC 8446 Section 4.4.2.2.

For the `s_server -xcert` callback, a minimal direction is to avoid replacing an already selected chain that has `CERT_PKEY_CA_SIGNATURE` with a later chain lacking that flag. A stricter callback can require:

```c
(rv & (CERT_PKEY_VALID | CERT_PKEY_CA_SIGNATURE))
    == (CERT_PKEY_VALID | CERT_PKEY_CA_SIGNATURE)
```

before selecting a chain, while retaining a fallback path for the case where no fully compatible chain exists.
