# TLS 1.3 aborts instead of sending a fallback certificate chain


OpenSSL's TLS 1.3 server path can abort with `handshake_failure` when the client's `signature_algorithms_cert` extension excludes the configured certificate's issuer signature algorithm, even though the client's `signature_algorithms` extension still offers a valid TLS 1.3 `CertificateVerify` algorithm.

RFC 8446 recommends a different behavior for this condition: if the server cannot produce a chain signed only with the indicated supported certificate-signature algorithms, it should continue by sending a fallback certificate chain of its choice. This is a confirmed `SHOULD`-level interoperability issue, not a hard `MUST` violation.

## Standard Requirement

- Official standard: [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446)
- Primary section: Section 4.4.2.2, Server Certificate Selection
- Supporting sections: Section 4.2.3, Signature Algorithms; Section 4.4.3, CertificateVerify

RFC 8446 separates the two client signature algorithm signals:

```text
The "signature_algorithms_cert" extension applies to signatures in
certificates, and the "signature_algorithms" extension ... applies to
signatures in CertificateVerify messages.
```

For server certificate selection, RFC 8446 states:

```text
If the server cannot produce a certificate chain that is signed only
via the indicated supported algorithms, then it SHOULD continue the
handshake by sending the client a certificate chain of its choice
that may include algorithms that are not known to be supported by the
client.
```

The same section limits fallback chains using SHA-1:

```text
This fallback chain SHOULD NOT use the deprecated SHA-1 hash
algorithm in general, but MAY do so if the client's advertisement
permits it, and MUST NOT do so otherwise.
```

For `CertificateVerify`, RFC 8446 still requires the server's signature algorithm to come from the client's `signature_algorithms` extension, except for the standard's chain-production exception. RSA `CertificateVerify` signatures in TLS 1.3 must use RSASSA-PSS, and SHA-1 must not be used there.

Interpretation: when the client provides a usable TLS 1.3 `signature_algorithms` value for `CertificateVerify`, but `signature_algorithms_cert` prevents the server from constructing a fully matching certificate chain, the server should not abort solely because no such fully matching chain is available. It should attempt the RFC fallback-chain behavior, subject to the SHA-1 restriction above.

static int check_cert_usable(SSL_CONNECTION *s, const SIGALG_LOOKUP *sig,
    X509 *x, EVP_PKEY *pkey)
{
    const SIGALG_LOOKUP *lu;
    int mdnid, pknid, supported;
    size_t i;
    const char *mdname = NULL;
    SSL_CTX *sctx = SSL_CONNECTION_GET_CTX(s);

    if (sig->hash != NID_undef)
        mdname = OBJ_nid2sn(sig->hash);
    supported = EVP_PKEY_digestsign_supports_digest(pkey, sctx->libctx,
        mdname,
        sctx->propq);
    if (supported <= 0)
        return 0;

    /*
     * The TLS 1.3 signature_algorithms_cert extension places restrictions
     * on the sigalg with which the certificate was signed (by its issuer).
     */
    if (s->s3.tmp.peer_cert_sigalgs != NULL) {
        if (!X509_get_signature_info(x, &mdnid, &pknid, NULL, NULL))
            return 0;
        for (i = 0; i < s->s3.tmp.peer_cert_sigalgslen; i++) {
            lu = tls1_lookup_sigalg(SSL_CONNECTION_GET_CTX(s),
                s->s3.tmp.peer_cert_sigalgs[i]);
            if (lu == NULL)
                continue;

            if (mdnid == lu->hash && pknid == lu->sig)
                return 1;
        }
        return 0;
    }

    return 1;
}

This check rejects the configured certificate when its issuer signature does not match any value in `peer_cert_sigalgs`.

    size_t i;
    int curve = -1;

    SSL_CTX *sctx = SSL_CONNECTION_GET_CTX(s);

    for (i = 0; i < s->shared_sigalgslen; i++) {
        lu = s->shared_sigalgs[i];
        if (lu->hash == NID_sha1
            || lu->hash == NID_sha224
            || lu->sig == EVP_PKEY_DSA
            || lu->sig == EVP_PKEY_RSA
            || !tls_sigalg_compat(s, lu))

        if (!tls1_lookup_md(sctx, lu, NULL))

        if ((pkey == NULL && !has_usable_cert(s, lu, -1))
            || (pkey != NULL && !is_cert_usable(s, lu, x, pkey)))

        tmppkey = (pkey != NULL) ? pkey
                                 : s->cert->pkeys[lu->sig_idx].privatekey;

        if (lu->sig == EVP_PKEY_EC) {
            if (curve == -1)
                curve = ssl_get_EC_curve_nid(tmppkey);
            if (lu->curve != NID_undef && curve != lu->curve)

            if (!rsa_pss_check_min_key_size(sctx, tmppkey, lu))
                continue;
        }
        break;
    }

    if (i == s->shared_sigalgslen)
        return NULL;

    return lu;
}

## Implementation Behavior

The TLS 1.3 server path handles the two extensions correctly at parse time, but later couples certificate-chain signature compatibility with fatal `CertificateVerify` signature-algorithm selection.

The practical consequence is:

1. The client sends a valid TLS 1.3 `signature_algorithms` list that can support the server's `CertificateVerify`.
2. The client also sends `signature_algorithms_cert`, but that list does not include the signature algorithm used to sign the configured server certificate.
3. `check_cert_usable()` rejects the configured certificate because its issuer signature is not in `peer_cert_sigalgs`.
4. `find_sig_alg()` returns `NULL`.
5. `tls_choose_sigalg(..., fatalerrs=1)` aborts with `SSL_R_NO_SUITABLE_SIGNATURE_ALGORITHM`.
6. The server sends `handshake_failure` before emitting a fallback `Certificate` chain.

This is not the same as a client omitting `signature_algorithms`, or sending no TLS 1.3-valid `CertificateVerify` algorithm. Those cases can correctly be fatal. The issue is the narrower case where the client does provide a valid `CertificateVerify` algorithm, but the server lacks a certificate chain fully matching `signature_algorithms_cert`.

## Inconsistency Reason

RFC 8446 says that when the server cannot produce a certificate chain signed only with the client-indicated supported algorithms, it `SHOULD continue` by sending a fallback chain of its choice, subject to the SHA-1 restrictions.

OpenSSL instead treats the unavailable matching chain as a fatal certificate/signature selection failure. The server aborts before sending any fallback chain, even though the client has offered a usable TLS 1.3 `CertificateVerify` algorithm.

Because the RFC language is `SHOULD`, this is a confirmed recommendation-level interoperability issue rather than a strict mandatory-protocol violation.

## Impact

A TLS 1.3 client that advertises a restrictive or implementation-specific `signature_algorithms_cert` list can receive an immediate fatal handshake failure from OpenSSL instead of receiving a fallback certificate chain and deciding locally whether the chain is acceptable.

This may reduce interoperability with clients that distinguish supported certificate-signature algorithms from supported `CertificateVerify` algorithms, which is exactly the use case RFC 8446 introduced `signature_algorithms_cert` to express.

## Fix Direction

Separate TLS 1.3 `CertificateVerify` signature selection from fallback certificate-chain selection. If the client's `signature_algorithms` extension contains a usable TLS 1.3 signing algorithm for the server's key, but `signature_algorithms_cert` rejects all available fully matching chains, the server should choose and send a fallback chain instead of immediately calling `SSLfatal()`.

The hard-failure behavior should remain for cases where the client omits `signature_algorithms`, sends an empty or malformed extension, or provides no TLS 1.3-valid `CertificateVerify` algorithm compatible with the server's end-entity key.
