# TLS 1.3 certificate selection ignores the signature_algorithms fallback for certificate signatures

## Summary

OpenSSL's TLS 1.3 server certificate selection path can send a SHA-1 signed certificate even when the client advertises only SHA-256-capable signature schemes and does not advertise SHA-1.

The issue is not limited to a missing preference heuristic. RFC 8446 says that when `signature_algorithms_cert` is absent, `signature_algorithms` also applies to certificate signatures. In the tested OpenSSL path, the client did not send SHA-1 in `signature_algorithms`, yet the server still completed the TLS 1.3 handshake with a `sha1WithRSAEncryption` end-entity certificate.

The same root cause affects TLS 1.3 client authentication. When a server's `CertificateRequest` contains only `signature_algorithms`, an OpenSSL client can send a client certificate whose issuer signature algorithm is outside that list. A focused run advertised only `rsa_pss_pss_sha256`; the client still sent a certificate signed with `sha256WithRSAEncryption`, and the handshake completed.

Both directions reach `check_cert_usable()`, which checks certificate signatures only when `peer_cert_sigalgs` is non-NULL and otherwise returns success instead of falling back to `peer_sigalgs`.

## Standard Requirement

- Official standard: <https://www.rfc-editor.org/rfc/rfc8446.html>
- Section 4.2.3, Signature Algorithms
- Section 4.3.2, Certificate Request
- Section 4.4.2.2, Server Certificate Selection
- Section 4.4.2.3, Client Certificate Selection

RFC 8446 Section 4.2.3 states:

```text
If no "signature_algorithms_cert" extension is present, then the
"signature_algorithms" extension also applies to signatures appearing
in certificates.
```

RFC 8446 Section 4.2.3 also states:

```text
TLS 1.3 servers MUST NOT offer a SHA-1 signed certificate unless no
valid certificate chain can be produced without it (see Section 4.4.2.2).
```

RFC 8446 Section 4.4.2.2 states:

```text
This fallback chain SHOULD NOT use the deprecated SHA-1 hash algorithm
in general, but MAY do so if the client's advertisement permits it, and
MUST NOT do so otherwise.
```

Interpretation: if the client does not send `signature_algorithms_cert`, the server must use the client's `signature_algorithms` list when deciding whether certificate signatures are acceptable. A SHA-1 signed certificate or fallback chain is forbidden unless the client's advertisement permits SHA-1, and a server must not offer SHA-1 when a valid non-SHA-1 chain can be produced.

For TLS 1.3 client authentication, `CertificateRequest` must contain `signature_algorithms`, while `signature_algorithms_cert` is optional. RFC 8446 requires the selected client certificates to be signed using an acceptable signature algorithm. Consequently, if `signature_algorithms_cert` is absent, the client must apply the server's `signature_algorithms` list to certificate signatures, except for the standard trust-anchor or self-signed path-start exception.

## Implementation Behavior

When `signature_algorithms_cert` is absent, OpenSSL accepts an otherwise usable certificate without checking that the certificate's issuer signature algorithm appears in the peer's `signature_algorithms` list. The code can still choose a valid TLS `CertificateVerify` algorithm, but that is separate from the X.509 certificate signature algorithm.

On the server-authentication path, this permits a server certificate signed with SHA-1 even though the client advertised no SHA-1 scheme. On the client-authentication path, `peer_sigalgs` is used to choose a viable `CertificateVerify` signature for the configured private key, but it is not used as the fallback policy for the certificate's own issuer signature. The client can therefore send a certificate outside the effective certificate-signature list in `CertificateRequest`.

The `s_server` multi-certificate callback also demonstrates that OpenSSL can treat both SHA-1 and SHA-256 alternatives as valid and then select based on configuration order rather than preferring the non-SHA-1 certificate:

```c
/* implementions/openssl-master/apps/lib/s_cb.c:1072 */
while (exc != NULL) {
    i++;
    rv = SSL_check_chain(ssl, exc->cert, exc->key, exc->chain);
    ...
    if (rv & CERT_PKEY_VALID) {
        if (!SSL_use_certificate(ssl, exc->cert)
            || !SSL_use_PrivateKey(ssl, exc->key)) {
            return 0;
        }
        ...
    }
    exc = exc->prev;
}
```

Because the loop does not stop after the first acceptable non-SHA-1 certificate and does not rank by certificate signature hash, the last valid candidate can win.

## Inconsistency Reason

RFC 8446 requires each endpoint selecting a local certificate to respect the peer's advertised certificate signature capabilities. If `signature_algorithms_cert` is absent, `signature_algorithms` applies to signatures in both server and client certificates. For server authentication, RFC 8446 additionally prohibits SHA-1 fallback unless the client advertisement permits it.

OpenSSL instead checks certificate signatures against `peer_cert_sigalgs` only when `signature_algorithms_cert` was supplied. Without that extension, `check_cert_usable()` accepts any certificate with a viable public key rather than using the available `peer_sigalgs` list. Runtime evidence confirms both consequences: a client advertising only `rsa_pss_rsae_sha256:rsa_pkcs1_sha256` receives a `sha1WithRSAEncryption` server certificate, and a client receiving a `CertificateRequest` limited to `rsa_pss_pss_sha256` sends a certificate signed with `sha256WithRSAEncryption`.

### Client-certificate selection direction

The client certificate used in this focused run has an RSA-PSS public key, but its X.509 certificate signature is PKCS#1 SHA-256:

Observed certificate properties:

```text
Signature Algorithm: sha256WithRSAEncryption
Issuer: CN=Root CA
Subject: CN=Client-RSA-PSS
Public Key Algorithm: rsassaPss
Signature Algorithm: sha256WithRSAEncryption
```

The TLS 1.3 server required client authentication and advertised only `rsa_pss_pss_sha256`. The client connected with the inspected certificate and key while handshake messages and state transitions were recorded.

Key observed output:

```text
client_rc=0 server_rc=0
<<< TLS 1.3, Handshake [length 000f], CertificateRequest
    0d 00 00 0b 00 00 08 00 0d 00 04 00 02 08 09
SSL_connect:SSLv3/TLS write client certificate
SSL_connect:SSLv3/TLS write certificate verify
SSL_connect:SSL negotiation finished successfully
Peer signature type: rsa_pss_pss_sha256
Signature Algorithm: sha256WithRSAEncryption
```

The `CertificateRequest` contains extension `0x000d` (`signature_algorithms`) with the single scheme `0x0809` (`rsa_pss_pss_sha256`). No `0x0032` (`signature_algorithms_cert`) extension is present. Under RFC 8446, the normal signature-algorithm list therefore also applies to certificate signatures. The client nevertheless sent a certificate signed with `sha256WithRSAEncryption`, confirming the client-authentication manifestation of the shared defect.

## Impact

On the server-authentication path, an OpenSSL server can send a SHA-1 signed certificate to a client that did not advertise SHA-1 support. Strict clients may abort certificate validation, while permissive clients may complete a handshake the server should not have offered.

On the client-authentication path, an OpenSSL client may send a certificate whose signature violates the effective policy in the server's `CertificateRequest`. A strict server may fail the handshake after receiving the non-compliant certificate; a permissive server may complete with a chain the client should not have selected.

## Fix Direction

For TLS 1.3 local certificate selection, OpenSSL should compute one effective certificate-signature algorithm list:

- Use `peer_cert_sigalgs` when `signature_algorithms_cert` is present.
- Otherwise use `peer_sigalgs`, as required by the RFC 8446 fallback rule.

Apply that effective list before emitting either a server or client `Certificate` message, while preserving the RFC exception for self-signed certificates and trust anchors that begin the certification path. SHA-1 signed server certificates must be rejected unless the client advertisement permits the relevant SHA-1 scheme and no valid non-SHA-1 chain can be produced.
