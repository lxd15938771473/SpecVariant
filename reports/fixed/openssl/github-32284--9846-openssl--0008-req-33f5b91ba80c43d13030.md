# RFC 9846 issue: OpenSSL accepts unrequested `external_id_hash` responses

- Recheck date: 2026-08-10

## Finding

The issue is real, but the precise defect is narrower than "OpenSSL does not implement `external_id_hash`".

OpenSSL does not have built-in support for extension type 55 (`external_id_hash`). That absence is not itself a protocol violation, because RFC 9846 lists TLS 1.3 recommended and allowed extensions but does not require every implementation to implement every listed extension.

The confirmed behavioral defect is on the receive path: when a TLS 1.3 server sends extension type 55 as an unrequested extension response, OpenSSL's client silently accepts it and completes the handshake. RFC 9846 requires the receiver to abort such a handshake with `unsupported_extension`.

## Standard Check

- [RFC 9846 Section 4.3, `Extensions`](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.3) defines `external_id_hash(55)` and lists `external_id_hash [RFC8844]` only for `CH, EE`.
- [RFC 9846 Section 4.3](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.3) limits the extension list to extensions marked recommended and allowed for TLS 1.3 at the time of writing; this is not an implementation mandate for every extension.
- [RFC 9846 Section 4.3](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.3) forbids trailing data in `extension_data` for implemented extensions, while excluding extensions the receiver does not implement or is configured to ignore. This sentence is about parsing an extension's body, not about permitting unrequested server extension responses.
- [RFC 9846 Section 4.3](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.3) defines TLS extensions as generally request/response structured: the client sends extension requests in `ClientHello`, and the server sends extension responses in `ServerHello`, `EncryptedExtensions`, `HelloRetryRequest`, and `Certificate`.
- [RFC 9846 Section 4.3](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.3) says implementations must not send extension responses in those server response messages unless the peer sent the corresponding request, except `cookie` in `HelloRetryRequest`; a receiver must abort with `unsupported_extension`.
- [RFC 9846 Section 4.3](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.3) says a recognized extension in a message where it is not specified must cause `illegal_parameter`.

Interpretation:

`external_id_hash` support is optional. However, once a server sends type 55 in a TLS 1.3 response message without a corresponding client request, the receiver-side response-extension rule in [RFC 9846 Section 4.3](https://www.rfc-editor.org/rfc/rfc9846.html#section-4.3) applies. In `Certificate`, type 55 is also outside the `CH, EE` placement listed by the table.

## Code Check

OpenSSL has no built-in symbol or `ext_defs` entry for `external_id_hash`:

- `implementions/openssl-master/include/openssl/tls1.h:153-163`: nearby TLS 1.3 extension constants include 41, 42, 43, 44, 45, 47, 49, 50, 51, and 57, but not 55.
- `implementions/openssl-master/ssl/statem/extensions.c:186`: built-in extensions are defined in `ext_defs`; there is no `external_id_hash` entry.

The relevant receive behavior is the unknown-extension path:

- `implementions/openssl-master/ssl/statem/extensions.c:747-749`: `verify_extension()` treats an unknown extension as allowed and sets `found` to null.
- `implementions/openssl-master/ssl/statem/extensions.c:958-968`: `tls_collect_extensions()` skips unknown extensions when `thisex == NULL`.
- `implementions/openssl-master/ssl/statem/extensions.c:970-999`: the check for unsolicited extension responses is below that skip and therefore only runs for recognized extensions.
- `implementions/openssl-master/ssl/statem/statem_clnt.c:4489-4493`: TLS 1.3 `EncryptedExtensions` processing calls `tls_collect_extensions()` and then parses collected extensions; it does not call `tls_validate_no_unknown_extensions()`.
- `implementions/openssl-master/ssl/statem/statem_clnt.c:2423-2428`: TLS 1.3 `Certificate` extension processing follows the same collect/parse path.
- `implementions/openssl-master/ssl/statem/statem_clnt.c:1964-1966`: TLS 1.3 `ServerHello` does call `tls_validate_no_unknown_extensions()`, showing that OpenSSL has a stricter unknown-extension validation helper but does not apply it to these later server messages.

This explains the observed behavior: type 55 is not recognized, so it is skipped before OpenSSL can enforce the unrequested-response rule.

## Runtime Evidence

On 2026-08-10, I reran the TLSProxy EncryptedExtensions and Certificate probes against the OpenSSL build in `implementions/openssl-master` using the `p_ossltest` provider. The negative probes injected extension type 55 without a matching client request, and the control injected a recognized invalid extension type to confirm that the harness observes client-side fatal alerts.

### Probe 1: type 55 in `EncryptedExtensions`

The probe injected extension type 55 into the server's TLS 1.3 `EncryptedExtensions`.

```text
MODIFY EncryptedExtensions add extension 55
EXT_TYPE 55
INJECTED 1
SUCCESS 1
TLS13 1
ALERT_SIDE server
ALERT_DESC 0
```

Result: OpenSSL completed the TLS 1.3 handshake. No client fatal alert was observed.

### Probe 2: type 55 in `Certificate`

The probe injected extension type 55 into the server's TLS 1.3 `Certificate` message.

```text
MODIFY Certificate add extension 55
EXT_TYPE 55
INJECTED 1
SUCCESS 1
TLS13 1
ALERT_SIDE server
ALERT_DESC 0
```

Result: OpenSSL completed the TLS 1.3 handshake. This is invalid both as an unrequested server extension response and as a placement outside the `external_id_hash` `CH, EE` table entry.

### Control Probe: recognized invalid extension in `EncryptedExtensions`

The control probe injected extension type 43 (`supported_versions`) into `EncryptedExtensions`.

```text
MODIFY EncryptedExtensions add extension 43
[2, 47]
EXT_TYPE 43
INJECTED 1
SUCCESS 0
TLS13 1
ALERT_SIDE client
ALERT_DESC 47
```

Result: OpenSSL rejected the recognized invalid extension with a client-side fatal `illegal_parameter` alert. This confirms that the TLSProxy injection and alert-observation path is effective, and that the type 55 success result is caused by OpenSSL's unknown-extension handling.

## Decision

The standard does not require OpenSSL to implement `external_id_hash`, but it does require a TLS 1.3 endpoint to reject unrequested server extension responses. The code skips unknown extensions before the unsolicited-response check, and the live probes confirmed that OpenSSL accepts type 55 in both `EncryptedExtensions` and `Certificate`.
