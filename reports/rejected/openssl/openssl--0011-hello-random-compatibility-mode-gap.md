# OpenSSL hello-random compatibility modes overwrite the first 4 bytes with time()

Simple upstream report: with `SSL_MODE_SEND_CLIENTHELLO_TIME` / `SSL_MODE_SEND_SERVERHELLO_TIME` enabled, the first 4 bytes of ClientHello.random / ServerHello.random come from `time(NULL)` instead of a secure random number generator. Off by default; default configuration is RFC-compliant.

## Standard Description

Official standard: [RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html).

- RFC 8446, Section 4.1.2 (ClientHello.random): "random: 32 bytes generated by a secure random number generator."
- RFC 8446, Section 4.1.3 (ServerHello.random): "random: 32 bytes generated by a secure random number generator."
- RFC 8446, Section 4.1.3 (downgrade sentinel): "The last 8 bytes MUST be overwritten as described below if negotiating TLS 1.2 or TLS 1.1, but the remaining bytes MUST be random."
- RFC 8446, Appendix C.1: "A secure random number generator MUST be used."

## Code Description

- `ssl_fill_hello_random` (`ssl/s3_lib.c:5252`) fills the hello random field. By default all 32 bytes come from `RAND_bytes_ex` (CSPRNG).
- When the corresponding time-mode bit is set (client: `SSL_MODE_SEND_CLIENTHELLO_TIME`, called from `ssl/statem/statem_clnt.c:1443`; server: `SSL_MODE_SEND_SERVERHELLO_TIME`, called from `ssl/statem/statem_srvr.c:2146`), the function first writes `time(NULL)` into bytes 0-3 and then fills only the remaining `len - 4` bytes from `RAND_bytes_ex` (`ssl/s3_lib.c:5261-5263`). The TLS 1.2/1.1 downgrade sentinel is then copied over the last 8 bytes.
- The flags are defined in `include/openssl/ssl.h.in:523-524` (`0x00000020U` / `0x00000040U`) with the comment "for compatibility with hypothetical implementations that require it". They are opt-in via `SSL_CTX_set_mode` / `SSL_set_mode`, off by default, and are not documented in `doc/man3/SSL_CTX_set_mode.pod` or anywhere else in the documentation tree.

## Reason for Inconsistency

- With either mode enabled, the first 4 bytes of ClientHello.random / ServerHello.random come from `time(NULL)` instead of a secure random number generator, so the field is no longer "32 bytes generated by a secure random number generator" as required by RFC 8446 Sections 4.1.2 and 4.1.3.
- When the server time mode is enabled during a TLS 1.2/1.1 downgrade, bytes 0-3 are a timestamp, violating the requirement that the remaining bytes MUST be random (only the final 8-byte downgrade sentinel may be fixed).
- TLS 1.2 and below (RFC 5246) historically allowed the first 4 bytes to be a time value ("clocks are not required to be set correctly"), which is the origin of these compatibility flags (introduced by commit 2016265dfb, 2013). RFC 8446 changed the wording to require the whole 32-byte field to come from a secure RNG, so these flags are no longer compliant for TLS 1.3, nor for the TLS 1.2/1.1 downgrade case under Section 4.1.3.
- The default configuration is fully compliant; the deviation is reachable only by explicitly enabling these undocumented modes.
